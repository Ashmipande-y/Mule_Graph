# Stage 2: Dataset Preparation and XGBoost Baseline

Status: **implemented, trained, and evaluated**. ML-only, entirely inside `ml/`.
Not integrated with FastAPI, the database, or the frontend.

## Dataset selection: what was tried, and why the final choice isn't IBM AML

The brief's preferred dataset is IBM's "Transactions for Anti Money Laundering
(AML)". It was checked first, directly against Kaggle's own page metadata (fetched
2026-09-07):

- **License**: Community Data License Agreement -- Sharing -- Version 1.0
  (CDLA-Sharing-1.0).
- **Domain**: explicitly synthetic -- generated by an IBM agent-based simulator
  modeling a "virtual world" of individuals, companies, and banks; not real
  transactions.
- **Access**: Kaggle's own structured data for this dataset marks its download
  `distribution` as `"requiresSubscription": true` -- i.e. it requires a logged-in
  Kaggle account. This environment has no Kaggle credentials (no `~/.kaggle/`
  directory, no `kaggle` package, no API token), and none were available to
  configure. This is a real, verified access blocker, not an assumption.

The brief's named fallback, **Elliptic**, was checked the same way and hits the
same wall: also `"requiresSubscription": true` on Kaggle. Its license (CC
BY-NC-ND 4.0 -- non-commercial, no-derivatives) is also more restrictive than
IBM AML's, and its domain (Bitcoin transaction-graph node classification) is
further from UPI/mule-account fraud than AML would have been.

Rather than use an unverified third-party re-upload of either dataset (several
exist on Hugging Face, but carry no license/attribution metadata and can't be
checked against the original for integrity -- using one would fail the brief's own
"verify its source, terms" requirement, not satisfy it), the search continued for
something **directly, legitimately, and verifiably** downloadable.

**Chosen dataset: OpenML dataset id 1597 ("creditcard")**, the "Credit Card Fraud
Detection" dataset originally published by Andrea Dal Pozzolo, Olivier Caelen, and
Gianluca Bontempi (Machine Learning Group, Universite Libre de Bruxelles, with
Worldline). Verified directly:

- **Source**: https://www.openml.org/search?type=data&id=1597
- **License**: recorded by OpenML as `"Public"`.
- **Direct download, no login required**:
  `https://data.openml.org/datasets/0000/1597/dataset_1597.pq` -- confirmed with a
  plain `curl`, HTTP 200, no auth prompt.
- **Integrity verified**: downloaded file MD5 `1593844f40edbdabaf5bddec4649e1c4`
  matches the server's `ETag` for that URL exactly. Loaded with pandas and
  confirmed row count (284,807), column list, and fraud count (492) match
  OpenML's own published quality metadata exactly.
- **Citation**: Dal Pozzolo, Caelen, Johnson, Bontempi, "Calibrating Probability
  with Undersampling for Unbalanced Classification", IEEE CIDM 2015.

### Domain, stated plainly (per the brief's explicit requirement)

This is **real** (not synthetic) European credit-card transaction data from
September 2013, over a two-day window: card-present/card-not-present payment-card
fraud. It is **not** account-to-account money-laundering or mule-network fraud,
and it has **no account or sender/receiver graph structure at all** -- each row is
one anonymized transaction (`V1`..`V28` are PCA-transformed features whose
original meaning is undisclosed for confidentiality, plus `Time` and `Amount`),
with no cardholder or account identifier of any kind.

This is a genuine domain mismatch with MuleGraph's actual problem (per the
original brief: "Bitcoin or AML results are not validated UPI fraud results" --
the same caveat applies here, arguably more strongly, since this isn't even a
network/graph dataset). It was chosen because it is the closest **real**,
**openly and verifiably licensed**, **directly downloadable** labeled fraud
dataset found, given that both of the brief's named AML-relevant candidates are
gated behind Kaggle authentication this environment doesn't have. See
Limitations below for exactly what this baseline can and can't tell us.

## Prediction unit, label, decision time

- **Prediction unit**: one transaction (one row). There is no account entity in
  this dataset, so the brief's specific warning -- "do not turn transaction
  labels into account labels without documenting the rule" -- doesn't arise here:
  there is nothing to aggregate up to. This is itself a limitation relative to
  MuleGraph's account-graph model, not a workaround of the warning.
- **Label**: `Class` -- 1 if the original data providers labeled the transaction
  fraudulent, 0 otherwise. The labeling/investigation methodology is not
  disclosed (confidentiality) -- documented as a limitation, not glossed over.
- **Decision time**: `Time` (seconds elapsed since the first transaction in the
  dump). Used only to order rows chronologically for the split (see below); the
  raw value itself is deliberately excluded from the feature set (see
  `features.py` docstring) because it would let the model key on "where in this
  specific two-day dump" rather than a generalizable time-of-day signal.

## Split: leakage-safe, and honestly, only partially

`xgb_baseline/dataset.chronological_split()`: sort by `Time`, then take
contiguous blocks -- first 60% train, next 20% validation, last 20% test. No
shuffling, no stratification. Verified before committing to this split that all
three blocks contain both classes (train: 360 fraud / 170,524 legitimate;
validation: 57 fraud / 56,904 legitimate; test: 75 fraud / 56,887 legitimate) --
this is checked by `test_every_split_contains_both_classes`, not assumed.

This is an **inductive (temporal)** evaluation: every validation transaction
occurs at or after every training transaction, and every test transaction occurs
at or after every validation transaction, within the dataset's two-day window.
No preprocessing statistics are fit across splits, because there are none to fit
-- features are raw PCA components plus `Amount` and a stateless derived
`hour_of_window`; XGBoost trees need no scaling, so there's no fitted
transformer that could accidentally see validation/test data.

**Honest limitation**: this dataset provides no cardholder/account identifier.
Unlike the mule-account graph setting MuleGraph actually targets -- where
preventing "the same account's other transactions leaking across the split"
would be essential -- there is no way to check for that kind of entity-level
leakage here, because there's no entity to check. The chronological split
prevents time-based leakage; it cannot address an entity-based leakage
dimension that doesn't exist in this particular dataset. This is exactly the
category of limitation the brief said to document rather than gloss over.

## Feature extraction (`xgb_baseline/features.py`)

`FEATURE_COLUMNS = V1..V28, Amount, hour_of_window` -- fixed order, saved with
the model, reconstructed identically at inference time. No fitted
preprocessing: `extract_features()` is a pure function of its input, verified by
`test_is_stateless_across_calls` (calling it twice on the same input yields
identical output).

## Model, training, and what gets saved

`xgb_baseline/train.py`: `XGBClassifier`, CPU only (`tree_method="hist"`,
`device="cpu"` -- explicitly not `"cuda"`; no GPU build of xgboost is installed,
per `ml/docs/ml/environment.md`'s finding that this machine's PyTorch install is
CPU-only and CUDA readiness for any framework here is unverified).
`scale_pos_weight` compensates for the ~0.17% positive rate (chosen over
resampling, which would add a second fit-on-train-only preprocessing step for no
clear benefit here). Fixed `random_state=42`.

Saved to `ml/models/xgb_baseline.joblib` (gitignored, per Stage 0's
`.gitignore`) as a single bundle: `{"model": ..., "metadata": {...}}`. The
metadata includes: feature column order and names, label column and mapping,
seed, full split description (method, fractions, per-split row/fraud counts),
full dataset provenance (source, license, citation, verified counts, verified
MD5), the threshold chosen on validation, how it was chosen, both validation and
test metric reports in full, xgboost/Python versions, and an explicit note that
`predict_proba` is a genuine model output but has not been separately
calibrated. A copy of the metadata is also written to
`ml/reports/xgb_baseline_metrics.json` for easy reading without unpickling the
model.

## Standalone inference (`xgb_baseline/inference.py`)

`load_model(path)` loads the bundle; `predict(loaded, rows)` extracts features
(via the same stateless `extract_features` used in training) and returns
`score` (the model's fraud-probability estimate) and `is_fraud` (score >=
the threshold saved at training time). `inference.py` imports nothing from
`train.py` -- verified by `test_inference_does_not_import_train_module` and by
grepping its actual import list. This mirrors how a future backend integration
would use the model: load the artifact, score rows, done -- no training-time
state needed beyond what's in the saved bundle.

## Proposed inference interface (proposal only -- not agreed with Smit)

For a future integration, the natural shape mirrors `ml/rules`'s `Finding`
pattern but for a single-transaction model score:

```json
{
  "method": "xgb_baseline_v1",
  "transaction_id": "...",
  "score": 0.94,
  "is_fraud": true,
  "threshold": 0.95,
  "score_is_calibrated_probability": false
}
```

This is explicitly a proposal, not a frozen contract -- nothing in this codebase
assumes it, and it has not been discussed with Smit. It's recorded here so the
eventual integration conversation has a concrete starting point, per the same
instruction that applied to `ml/rules`'s `AccountRisk`.

## Limitations (read this before citing these numbers as "the model's accuracy")

1. **Domain mismatch**: real credit-card fraud, not AML/mule-network fraud. These
   metrics say the *pipeline* (data loading, feature extraction, chronological
   split, training, threshold selection, evaluation, save/load, inference) works
   correctly end to end on a real, verifiably labeled, imbalanced fraud
   classification problem. They say nothing about how well an XGBoost model
   would perform on actual UPI transaction data or actual mule-account
   detection -- that would need IBM AML (or equivalent) once Kaggle access is
   available, or a different dataset choice.
2. **No account/graph structure**: this dataset cannot exercise or validate any
   of the graph-based feature engineering that would matter for MuleGraph's
   actual use case (e.g. features derived from `ml/rules`'s fan-out/convergence
   evidence). The XGBoost pipeline built here is dataset-shape-agnostic (feature
   list is just a fixed set of named columns), so re-pointing it at a different,
   properly account-structured dataset would not require a redesign, but it
   would require new feature engineering.
3. **Undisclosed label methodology**: `Class` is taken as ground truth without
   being able to audit how the original providers determined it.
4. **No entity-level leakage check available**: see the split section above.
5. **`predict_proba` is not separately calibrated**: treat `score` as a ranking
   signal, not a calibrated probability, until calibration is added (this is a
   different caveat from `ml/rules`'s heuristic score, which is not a model
   output at all -- both should be labeled distinctly to any future consumer).
6. **Baseline, not tuned**: hyperparameters (300 trees, depth 4, learning rate
   0.1) were chosen as reasonable CPU-fast defaults, not searched. This is a
   baseline to compare future work against, not a final model.
